## Restricciones, entregables y defensa

- **Expo SDK 57 / React Native / TypeScript**: versiones y Doctor confirmados. No se añadieron dependencias para esta revisión.
- **MockAPI /medidores y /lecturas**: el catastro se consulta por código exacto y se muestra con campos; las lecturas de `/lecturas` no se listan en la app. No se hicieron POST de prueba al servidor durante esta revisión.
- **Diseño no genérico**: icono de agua original, paleta y controles neumórficos en `src/theme/design.ts`; el efecto real y la legibilidad necesitan revisión visual física.
- **APK instalado en Android**: el solicitante confirmó que hará esta parte después. Se canceló el build EAS iniciado por el agente; la instalación y demostración física no se consideran verificadas. El perfil `preview` permanece configurado.
- **Repositorio Git y enlace**: el proyecto es Git local, pero `git remote -v` no muestra un remoto configurado; **no existe un enlace GitHub verificable aún**. Se debe publicar en un repositorio del estudiante y añadir su URL al documento original. No se atribuyen decisiones personales al estudiante: los ADR registran procedencia del solicitante y contribución de IA.
- **Defensa oral (4 p.)**: no es un requisito que pueda implementar o verificar IA. El estudiante debe demostrar app y explicar su elección técnica y código sin asistencia de IA en la fecha indicada por el documento.
- **Foto externa**: requisito opcional. La app conserva evidencia local, `fotoUrl=null` sin servicio externo; no se presume carga en la nube.

## Procedimiento de demostración recomendado (sin afirmar su ejecución)

1. Instalar **el APK actualizado**; no desinstalar la instalación anterior si tiene fotos/lecturas sin respaldo. Iniciar con EMP-001/Demo2026! y comprobar persistencia y cierre de sesión. Verificar que Inicio muestra Registros → Pendientes → Enviándose y no una sección «Lecturas en MockAPI».
2. Teclear `MED-123` y verificar error, ausencia de datos visibles y ausencia de GET por código inválido; consultar `MED-000001`, activar avión, repetir la consulta.
3. En avión iniciar medidor nuevo (`MED-000123`), registrar normal, cerrar desde recientes a mitad de formulario y reabrir: Continuar/Descartar. Guardar y observar `Pendiente de verificación`.
4. Repetir el mismo código y período: comprobar error bajo el campo «Código de medidor» y Continuar deshabilitado. Cambiar al mes siguiente: debe permitirse. Si hay conexión, la comprobación remota debe detectar una lectura de otro dispositivo.
5. Reconectar y comprobar en MockAPI una única fila con el mismo `clientId`. Si el medidor no existe, anterior/consumo siguen null; si existe, verificar cálculo y anomalía.
6. Probar normal sin lectura, inaccesible sin motivo, dañado sin descripción/foto; probar un consumo exactamente triple y uno superior al triple, confirmación física y permiso de cámara denegado.
7. Fotografiar, cerrar/reabrir, confirmar URI accesible; editar pendiente y comprobar restricción mensual. Con envío confirmado, comprobar sólo lectura.
8. Para interrupción de POST, usar una red de prueba o emulador controlado: comprobar que, si la fila remota existe, se reconcilia por `clientId` sin segundo POST; si el GET confirma ausencia, se reintenta una creación con el mismo `clientId`. La unicidad absoluta sigue dependiendo de que MockAPI no confirme tarde una escritura que el GET aún no muestra.

El único estado honesto de cumplimiento de la rúbrica debe asignarse **después** de esas comprobaciones físicas; este reporte no predice una nota. En particular, no se puede garantizar simultáneamente entrega automática de todo POST ambiguo y cero duplicados con MockAPI sin una operación idempotente en el servidor.
